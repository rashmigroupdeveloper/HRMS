# HRMS

Human Resource Management System, rebuilt step by step with a simple, conventional stack.
The database schema is added **one model at a time**; every feature is built on top of it.

## Stack

| Part | Technology |
|---|---|
| Backend | Node.js 22, Express 5, TypeScript 7 |
| API layer | oRPC 1.15 - typed procedures; the frontend gets backend types automatically |
| Database | PostgreSQL + Prisma 7 (schema, migrations, typed client) |
| Validation | zod 4 |
| Excel | exceljs 4.4 (employee import template + import, directory export) |
| Letters / e-mail | TipTap 3 (letter template editor), pdfmake 0.3 (offer letter PDFs), pdf-lib 1.17 (HR's paper forms printed filled in), Fontsource (Roboto - the PDF's default font, so the editor's pages break where the PDF's do - and the WordCraft open fonts for letters: Carlito, Caladea, Arimo, Tinos, Cousine, Inter, Source Sans 3, Source Serif 4, JetBrains Mono), nodemailer 10 (offer e-mails, one-time codes) |
| Frontend | React 19, Vite 8, TypeScript 7 |
| UI | Tailwind CSS 4 + shadcn/ui (Base UI) + lucide icons |
| Data fetching | TanStack Query 5 (through oRPC's query helpers) |
| Routing | React Router 8 |

Types flow in one direction, with nothing written twice:
Prisma schema -> Prisma client -> backend procedures -> frontend (`orpc.*`).
Rename a field in the schema and every place that uses it shows a TypeScript error.

## Getting started

Prerequisites: Node.js 22.12+ and PostgreSQL running locally.

```bash
# 1. Install everything (both apps) from the root
npm install

# 2. Create backend/.env from the example, set your DB password and generate DATA_ENCRYPTION_KEY
#    (command is in the file). Back the key up - without it encrypted Aadhaar/PAN/bank numbers are unreadable.
#    Uploaded documents go to backend/storage/ (STORAGE_DIR) - back that folder up with the database.
#    E-mail: set SMTP_* and MAIL_FROM to send offer e-mails; without SMTP_HOST they are saved as .eml files in
#    backend/storage/outbox/. APP_URL is the web address candidates open their offer link on.
cp backend/.env.example backend/.env

# 3. Create the database (once)
psql -U postgres -c "CREATE DATABASE hrms_new;"

# 4. Apply migrations (once there are models)
npm run db:migrate

# 5. Start backend + frontend together
npm run dev
```

- Tests: set `TEST_DATABASE_URL` in `backend/.env` (a database whose name ends in `_test`, see `.env.example`), then
  `npm run test`. The tests migrate it themselves and add their own uniquely named data - nothing is deleted.

- Frontend: http://localhost:5180 - log in with an employee code; on an empty database create the first super admin with `npm run create-admin`, later logins with `npm run set-password` or the Roles & access page.
  For testing, list accounts in `frontend/.env.development.local` (`VITE_TEST_ACCOUNTS`, see `frontend/.env.example`; never
  committed): the login page then shows them for one-click sign-in (development only, never in a production build).
- API: http://localhost:5200/api/rpc (health check: `POST /api/rpc/health/check`)

In development the frontend calls `/api/...` and Vite forwards it to the backend, so there are no CORS issues.

## API

**Every API is documented in [API_TRACKER.md](API_TRACKER.md)**: path, who can access it, input fields,
what it returns, what it does and its errors, plus the total count. Search it before adding an API so nothing
is built twice, and update it in the same change whenever an API changes (`npm run check:api-tracker` verifies).

## Adding a table

1. Add the model to the right domain file in `backend/prisma/schema/` (or create a new one, e.g.
   `organization.prisma`). Follow the conventions in `_base.prisma`.
2. `npm run db:migrate -- --name add_departments` - creates the SQL migration, applies it, and regenerates the
   typed client.
3. Commit the schema change **and** the new folder in `prisma/migrations/` together.

## Adding a feature

**Backend** - every request goes through three layers: `router -> service -> repository -> database`.
Create `backend/src/modules/<feature>/`:

| File | Layer | Responsibility |
|---|---|---|
| `<feature>.router.ts` | routes + controller | auth, input schema -> call one service function -> return. No logic. |
| `<feature>.service.ts` | business | rules and decisions (e.g. throw `NOT_FOUND`), transactions; calls repositories |
| `<feature>.repository.ts` | data access | the only place with Prisma queries; explicit `select`, never whole rows |
| `<feature>.schema.ts` | - | zod schemas for procedure inputs |
| `index.ts` | - | public API: the router + the service namespace (+ the schema namespace when other modules validate the same data); the repository stays private |

There is no separate controller layer - the oRPC procedure already is the controller.

```ts
// employees.repository.ts - data access
export function findByCode(employeeCode: string, db: DbClient = prisma) {
  return db.employee.findUnique({ where: { employeeCode }, select: employeeSelect })
}

// employees.service.ts - business rules
export async function getByCode(employeeCode: string, db?: DbClient) {
  const employee = await employeesRepository.findByCode(employeeCode, db)
  if (!employee) throw new ORPCError('NOT_FOUND', { message: `No employee found with code ${employeeCode}` })
  return employee
}

// departments.router.ts - routes + controller: who may call it (area + level), input, one service call
export const departmentsRouter = {
  list: authedProcedure.input(listInput).handler(({ input }) => departmentsService.listDepartments(input?.includeInactive)),
  create: accessProcedure('ORGANIZATION', 'WRITE')
    .input(createDepartmentInput)
    .handler(({ input }) => departmentsService.createDepartment(input)),
}
```

Then add the router to `backend/src/router.ts` (`employees: employeesRouter`).

**Access:** reading APIs use `accessProcedure(area, 'READ')`, changing APIs `accessProcedure(area, 'WRITE')`.
Roles are data (the "Roles & access" page), so code never names a role. Someone with several roles works in one at a
time: they pick it in the account menu (per tab), and only that role's areas and data access count. A new module adds its area to
`AccessArea` in `access.prisma` and its View / Edit text to `AREA_INFO` in `modules/accounts/roles/roles.service.ts`;
the frontend shows pages and buttons with `useAccess().can(area, level)`.

**Where every kind of file goes, naming, and the dependency rules are defined in [CLAUDE.md](CLAUDE.md)
(section 1, "Folder structure").** They apply to everyone - people and AI assistants. Follow them for every change;
the structure itself only changes by agreement, and then CLAUDE.md is updated in the same change.
Codex and other AI agents start from [AGENTS.md](AGENTS.md), which sends them to the same CLAUDE.md.

Errors: throw `new ORPCError('NOT_FOUND', { message: 'Department not found' })` for expected failures.
Invalid input (400 with a list of field issues) and common Prisma errors (duplicate -> 409, missing -> 404) are
converted automatically in `core/rpc/errors.ts`.

**Frontend** - no API types to write; they come from the backend:

```tsx
const departments = useQuery(orpc.departments.list.queryOptions())
const create = useMutation(orpc.departments.create.mutationOptions())
```

Dates and files work as-is: a `Date` returned by the backend arrives in the browser as a `Date`.
