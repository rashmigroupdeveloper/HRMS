# HRMS - rules for every change

A rewrite of the old HRMS (`../HRMS`). The old code is a **reference for business rules only** - do not copy its
architecture (Kysely, hand-written DB types, node-pg-migrate, multiple Postgres schemas, DB triggers, the OpenAPI
handler + hand-written frontend types). We use oRPC here too, but with the RPC handler and the typed client.

## 1. Folder structure - MANDATORY

Every file you create, edit, or move must fit the structure below.

- **Before adding code, find its place in the "Where does it go?" table.** Do not invent new top-level folders,
  new file roles, or new places for things.
- **When you edit code that is in the wrong place, move it to the right place as part of the change** (with
  `git mv`), and fix its imports.
- **The structure itself only changes with the user's approval.** If something truly does not fit, stop and propose
  where it should go. Once agreed, update this file and the README structure in the same change.
- Folders marked *(when needed)* do not exist yet. Create them when the first file needs them, never empty.

### The three layers (every module, every request)

```
router  ──►  service  ──►  repository  ──►  database
```

| Layer | Its job | Never |
|---|---|---|
| **router** (`<feature>.router.ts`) - routes + controller | Pick the procedure builder (auth/permission), `.input(schema)`, call **one** service function, return its result. Usually a one-liner. | Business logic, Prisma, try/catch |
| **service** (`<feature>.service.ts`) | Business rules and decisions (throw `ORPCError` `NOT_FOUND` / `CONFLICT` / `FORBIDDEN`...), combine repositories and other modules' services, run transactions. Function names: `getX` (throws if missing), `listX`, `createX`... | Query the database (`prisma.<model>`, `$queryRaw`). Only `prisma.$transaction` is allowed |
| **repository** (`<feature>.repository.ts`) | Prisma queries with an explicit `select` (never whole rows). Function names: `findX` (returns null if missing), `list`, `create`, `update`, `delete`. Last parameter `db: DbClient = prisma`. | Business rules, throwing `ORPCError`, calling services |

- **There is no separate controller layer** - the oRPC procedure already does the controller's job. Do not add
  `*.controller.ts` files.
- Every module has all three files, even when a layer is thin (e.g. a service that only calls one repository
  function and throws `NOT_FOUND`).
- Import layers as namespaces: `import * as employeesService from './employees.service.js'`,
  `import * as employeesRepository from './employees.repository.js'`.
- Transactions: the service opens one and passes `tx` down to every repository (and other modules' services, which
  accept an optional `db?: DbClient` and pass it on):

  ```ts
  await prisma.$transaction(async (tx) => {
    const application = await leaveRepository.createApplication(data, tx)
    await ledgerRepository.addEntry({ applicationId: application.id, days: -data.days }, tx)
  })
  ```

### Naming

- Backend: folders kebab-case; module folders are plural nouns (`employees`, `leave-types`); files
  `<name>.<role>.ts` where role is `router | service | schema | repository | jobs | test`.
- Frontend: components and pages PascalCase `.tsx` (`EmployeeCard.tsx`, `EmployeesPage.tsx`); hooks `useX.ts`;
  other files kebab-case `.ts`; feature folders kebab-case.
- Prisma: see the conventions at the top of `_base.prisma`.

### Dependency rules

1. One direction only: `router -> service -> repository -> database`. Never the reverse, never skip a layer
   (a router never imports a repository or `prisma`; a repository never imports a service).
2. `core/` and `shared/` never import from `modules/`. `shared/` never imports from `core/`.
3. Modules talk to each other only through `#modules/<name>` (resolves to that module's `index.ts`; deep imports
   don't compile), and only to the other module's **service** (and its exported **schemas**). No circular
   dependencies between modules.
4. Imports: `#core/...`, `#shared/...`, `#modules/<name>` across folders (aliases in `backend/package.json`
   "imports"); relative `./x.js` inside the same module or inside `core/`. Frontend uses `@/...`.

## 2. How we work

- The schema is built **one model at a time, together with the user**. Never add models, fields, or tables the user
  has not agreed to. Propose first, then implement.
- **No field without a real purpose.** Every column must be needed by a form (e.g. the joining form RML/HR/02/01),
  a statutory requirement (EPF, ESIC, gratuity, tax), or a concrete HR process - and its source is noted in a schema
  comment. Do not add "nice to have", speculative, or derivable fields (e.g. no `age` when `dateOfBirth` exists, no
  `probationMonths` when `probationEndDate` exists). Fields owned by a later module (payroll, attendance) wait for it.
- **Anything deferred goes into `BACKLOG.md` in the same change** ("later", "when login exists", "ask HR"),
  with why it waits and what it needs. Delete the item when it is done.
- Keep it simple and conventional. Do not add a new library without asking.
- Always use the latest stable version of a package.

## 3. Database (Prisma)

- `backend/prisma/schema/` is the single source of truth. Never hand-write SQL types or edit `src/generated/`.
- Naming: models PascalCase singular -> snake_case plural tables (`@@map`); fields camelCase -> snake_case
  columns (`@map`). Every model has `id`, `createdAt`, `createdById`, `updatedAt`, `updatedById` - all compulsory
  (timestamps as timestamptz); calendar dates use `@db.Date`.
- **Who did it:** every other column recording when something was done (`offerSentAt`, `reviewedAt`...) has a
  `<action>ById` next to it, set and cleared together. A "by" column holds the logged-in employee's id
  (`context.user.employeeId`) or `SYSTEM_ACTOR` (0) for scripts, migrations, jobs and the candidate on their own
  pages (shown as "Candidate (online)") - never an id from the request.
  Repository `create` / `update` functions take `actorId: ActorId` as a required parameter and add the columns with
  `createdBy(actorId)` / `updatedBy(actorId)` from `#core/db/prisma`; responses show people with
  `employeesService.lookupPeople` as `{ employeeCode, name }`, never raw ids.
- Business logic goes in TypeScript services, not in database triggers.
- **Change history is automatic** (decided 2026-11-16): every create / change / delete through `prisma` (and every
  transaction opened with `prisma.$transaction`) is recorded in `audit_logs` by `core/audit` - never write audit rows
  by hand, and never change data with raw SQL (`$executeRaw`), which would not be recorded. A new table is recorded
  without any extra code; a new secret column must end in `Encrypted`, `Hash` or `Token` so its values are hidden.
  Rows the system rebuilds wholesale from other records are left out (`SKIP_MODELS` in `core/audit/capture.ts`):
  attendance days, a pay run's people / salary copy (payroll stage 2, decided 2026-11-26 - each refresh is recorded
  on the run instead) and a pay run's days and worked-out lines (stage 3, approved 2026-11-27 - its copy of the locked
  attendance and the amounts worked out from it; each working-out is recorded on the run). People's decisions are never
  left out; adding a model there needs the user's approval.
- **Stored files - findable without the database** (decided 2026-11-13). Every file in file storage (uploads,
  generated PDFs, images) is named so that, if the database is lost, a person can still tell from the folder and file
  name whose file it is and what it is. The key is `<area>/<owner>/<what>/<date>_<random>.<ext>`:
  - `area` - the kind of record, plural kebab-case: `candidates`, `employees`, `offer-letters`, `letter-templates`.
  - `owner` - the record's lasting business key, readable: an employee's code (`RML035384`); a candidate's id +
    name (`183-neha-das`); a company code + offer number (`RML/RML-OFFER-2026-0001`); a template's id + name
    (`1-offer-letter`). Never only a database id or a random value.
  - `what` - what the file is, as the database names it: the document type (`AADHAAR_COPY`, `SIGNED_OFFER_LETTER`),
    the revision (`rev-1`), the image part (`HEADER`).
  - `<date>_<random>.<ext>` - the day it was stored (`2026-11-13`), a short random part so two files never clash,
    and the real extension from the detected file type (never the uploaded name - that is kept in the database).
  - Example: `employees/RML035384/AADHAAR_COPY/2026-11-13_7f3a9c21.pdf`,
    `offer-letters/RML/RML-OFFER-2026-0001/rev-0/2026-11-13_9e8f7a6b.pdf`.
  - Keys are built only by `core/storage` from cleaned parts (names lower-cased to `a-z 0-9 -`, length-limited) -
    never from raw request values, so no path tricks are possible.
  - When a file's owner changes (a candidate joins and becomes an employee), the file is moved to the new owner's
    folder and its key updated in the same step.

## 4. Backend code

- Build procedures from `#core/rpc/procedures` - never from bare `os`: `publicProcedure` (only `health.check`,
  `accounts.login`, the candidate's offer page `candidates.offerResponse.*`, which is keyed by a secret link
  token and needs a one-time code to answer - approved 2026-11-12 - `candidates.portal.signIn`, the same link +
  code, and "forgot password" on the sign-in page, `accounts.requestPasswordReset` and `accounts.resetPasswordWithCode`,
  which answer the same whatever the employee code is and need a one-time code e-mailed to the employee - approved
  2026-11-15), `candidateProcedure` (ONLY for `candidates.portal.*`: a candidate signed in to their own joining-form page
  with a session of its own, not an employee login; gives `context.candidate` and the handler works only on
  `context.candidate.candidateId`, never on an id from the request - approved 2026-11-13), `authedProcedure` (any
  logged-in employee, gives `context.user`), `selfServiceProcedure` (one's own action - applying for leave, comp-off,
  regularizations, shift changes: a logged-in employee with no active role, refused in the role portal - 2026-11-25; a
  mixed API calls `assertSelfService` from `#core/auth/access` on its own-record branch), or
  `accessProcedure(<area>, 'READ' | 'WRITE')` (READ = view, WRITE = change; WRITE includes READ), or
  `accessAllProcedure([area, level], ...)` when several areas are needed at once (a part of someone else's employee
  record: its area + `EMPLOYEES` View - the employee areas were split 2026-11-16; one's own record needs none, checked in
  the service with `seesPart` / `assertPart` from the employees module).
  `sessionProcedure` (also allowed with a temporary password) is ONLY for `accounts.me`, `accounts.logout` and
  `accounts.changePassword`.
- **Roles are data, areas are code.** Roles are created on the "Roles & access" page and give a level per area; an
  employee can have several. **One role at a time** (decided 2026-11-23): the user picks the active role in the account
  menu (per browser tab, sent as the `x-hrms-role` header); `resolveUser` checks it against the roles actually given and
  builds `context.user.access` and `grants` (data access) from that role alone - roles are never combined; an unknown or
  removed role = no role access (never another role silently). **Two portals** (the user, 2026-11-25 - replaces "no header
  = the lowest role id given"): no header = **Employee self-service**, no role at all - everyone signs in there, even a
  Super Admin; picking a role opens the **role portal**. One's own actions (leave, comp-off, regularizations, shift
  changes, one's own document uploads, withdrawing one's own requests) are done in self-service only and refused with a
  role active (`selfServiceProcedure` / `assertSelfService`). Approval steps naming a person (reporting / functional
  manager, HOD, escalation) are decided in self-service only; steps for a role, an area or the "Admin" fallback need that
  role active. Reading one's own record, the reporting tree and the HOD department work in both portals (the role portal's
  employee lists show the role's records plus one's own team - the user, 2026-11-25). Company payroll runs follow the
  stricter rule below. Code never names a role. A new module adds its area to `AccessArea`
  (`prisma/schema/access.prisma`) and its View / Edit text to `AREA_INFO` (`modules/accounts/roles/roles.service.ts`).
  Reading APIs use READ, changing APIs use WRITE. A rule that depends on the input (e.g. "own record, or EMPLOYEES
  READ") goes in the service with `assertAccess` from `#core/auth/access`.
- **Data access - whose records (decided 2026-11-18, BACKLOG 3a).** Each role given to an employee has rows of company ->
  plant -> department ("all" at any level) at View / Edit, worked out only by `core/auth/scope.ts`; only the active role's
  rows count. Every API that
  reads or changes people's records follows **section 8** - read it before writing or changing any API.
- **Payroll draft runs (approved 2026-11-26):** `/manage/payroll` uses the dedicated `PAYROLL` area, separate from
  an employee's `SALARY` profile access. Each run covers one whole company: View needs one active-role row covering
  every plant/department; creation needs Edit for that whole company. Partial rows are never stitched together, and
  reporting-tree/HOD access does not extend to payroll runs. Use `wholeCompanyScopeOf` for list/count/detail and
  `assertWholeSlice` for creation and every change inside a run. Stage 1 creates only regular monthly India drafts,
  unique per company/pay month; attendance dates are captured from the shared attendance cycle. **The days a run pays
  are those captured dates** (decided by the user, 2026-11-27: salary is for 26th to 25th, not the calendar month, and
  the start day stays changeable): the attendance cycle of the pay month, read
  only through `payPeriodOf` (`payroll/people/people.service.ts`); the start day is the Attendance setup setting, never a
  day or "calendar month" written in payroll code, and a run already created keeps its dates. Stage 2 (built
  2026-11-26, `payroll/people/`, `payroll/inputs/`) copies each run's people and the salary in force on each day and
  takes the month's inputs. Stage 3 (built 2026-11-27, `payroll/days/`, `payroll/calculation/`): "Work out pay"
  (`payroll.calculation.compute`) takes the run's OWN copy of each person's days from the LOCKED attendance, reading
  attendance only through `attendanceService` (`listPayrollDays`, `payrollLockOf`), and follows it half by half with no
  rule of its own - present, on duty, weekly off, holiday and paid leave are paid; absent, missed punch and leave without
  pay are unpaid (a half the late rule made absent too, unless regularized or corrected); an absent Saturday is half a
  day; what attendance does not say is "unclear", and that person's pay is held and listed, never guessed (the user,
  2026-11-27). **The money rule (decided by the user, 2026-11-27):** a day is worth the monthly amount / the days of the
  pay period; an earning is cut for unpaid days unless its component is marked "paid in full"
  (`SalaryComponent.cutForUnpaidDays`); each worked-out line is rounded once to the nearest rupee; inputs are paid as
  typed. The rule lives in one place (`payroll/calculation/calculation.service.ts`) and is checked against a greytHR
  salary register in the parallel run (BACKLOG item 31). Earned amounts are salary figures (`seesSalaries`, below).
  **Stage 4, deductions and net pay (built 2026-11-27, `payroll/deductions/`, `payroll/statutory/`,
  `payroll/tax-openings/`): rates are data** - every statutory rate, ceiling and slab is a dated row on Payroll ›
  Statutory settings (Payroll Edit for every company, `assertGroupWide`), entered from the notification, never seeded or
  written in code; a figure not in force, a missing work location / component / birth date, the old tax regime or a
  consultant without a typed TDS, or deductions above half of the wages HOLD the person (stored with the reason,
  `PayrollRunEmployee.heldFor`) - never a zero. Decided by the user: PF on the components marked "PF wages" up to the
  ceiling (per-person "PF on full wages"), for those whose statutory details say "PF applicable"; ESIC decided by the
  salary at the start of each ESIC period; professional tax and LWF by the work location's State; monthly TDS worked out
  (new regime, no declarations - those come in stage 7) or typed; no ESIC / professional tax / LWF for consultants (TDS
  typed), no ESIC for apprentices. Deductions and net are salary figures too (and the hold notes every Payroll viewer
  sees never carry an amount); opening tax figures follow whole-company Payroll scope by the employee's company, their
  amounts shown only with Salary View covering it as well. Approval and payment wait for their approved stages; no independent approval
  lifecycle is built into payroll.
  **Decided for stage 2 (the user, 2026-11-26):** monthly inputs are entered and changed only by someone with Payroll
  Edit covering the whole company - a plant-level HR person sends their figures to them; salary amounts inside a run
  (the salary copy and its lines) are shown only to a viewer who also has `SALARY` View covering the whole company
  (`seesSalaries` in `payroll/people/people.service.ts`) - Payroll alone shows the people, days and inputs but not the
  salaries; everyone on the company's rolls is in its run, consultants included. The coding plan is in BACKLOG item 31.
- **Employee document submissions (approved 2026-11-25):** an authenticated employee may upload only to their own
  record without HR Edit access. Files start pending, cannot satisfy evidence checks until HR verifies them, and do
  not replace a verified current copy while pending. Existing scoped HR management and sensitive-type access remain;
  an employee never reviews their own submission. Family/nominee requests are approved in principle but wait for
  their proposed schema/process (BACKLOG item 32); this exception does not allow direct profile editing.
- The frontend decides what to show with `useAccess().can(area, level)` and `useAccess().covers(area, level, where)` (from
  `accounts.me`), never with role names; the backend checks the same access on every call.
- Services throw `ORPCError` with a standard code for expected failures (`NOT_FOUND`, `CONFLICT`, `FORBIDDEN`, ...).
  Validation and Prisma errors (duplicate, not found, foreign key) are mapped centrally in `core/rpc/errors.ts`;
  don't re-map them in routers or services.
- Database types and enums come from `#core/db/prisma` (re-exported generated client).
- Every procedure that returns personal data needs at least `authedProcedure`.
- Code under `backend/src` is also type-checked by the frontend (via `import type`), so use erasable TypeScript only:
  no `enum`, no `namespace`, no constructor parameter properties.
- ESM with `nodenext`: relative imports end in `.js`.
- Read config only through `#core/config/env`.

## 5. Frontend code

- Call the backend only through `@/lib/orpc`: `useQuery(orpc.x.y.queryOptions(...))`,
  `useMutation(orpc.x.y.mutationOptions())`. Never hand-write API request/response types.
- `@backend/*` may only be used with `import type`.
- **Two portals, two address trees** (the user, 2026-11-25): `/ess/...` is Employee self-service (one's own record and
  actions, one's team and HOD department), `/manage/...` the role portal - never `/admin`, as a role can be called anything.
  Each page is registered under the portal it belongs to (`RequirePortal` shows the switch screen in the other one); a page
  in both builds its links with `usePortal().to(...)`, a page in one portal links with its full `/ess/` or `/manage/`
  address. The menu follows the tab's choice (`portalOf(me.activeRoleId)`); an old address goes on with `MovedToPortal`.
- shadcn components use Base UI: compose with the `render` prop, not `asChild`.
- **Unsaved input is never lost by accident** (decided 2026-11-17). Every add / edit form opens in `FormDrawer`
  (`@/components/FormDrawer`) or, for a small form in a centred dialog, `FormDialog` (`@/components/FormDialog`) - never
  a bare `Dialog` with inputs. A click outside never closes them; give them `dirty` (the input differs from what the
  form opened with, false once saved) so X / Esc / Cancel ask "Discard your changes?" first; Cancel is `<DrawerCancel />`
  / `<DialogCancel />`, never a button that closes directly. A page with a form asks before leaving with unsaved
  changes (as the letter-template page does).
- **Every page shows a skeleton while it loads** (decided 2026-11-21). Whenever you create a page, or change a page or
  section that loads data, its loading state (`isPending`) is a skeleton shaped like the real content - never
  "Loading…" text, a spinner or an empty area, and never `animate-pulse` boxes drawn by hand:
  - **It looks like the real UI with only the data missing** (the user, 2026-11-22). Same containers, cards, grids,
    paddings and order as the loaded page; every text that does not come from the data stays real text - page and card
    titles, field labels, column headings, tab and menu names, legends, the calendar's weekdays, icons. Only the values
    (names, numbers, dates, statuses, rows of records) become grey bars, sized like a typical value. Generic bars in
    place of a real card title or label are wrong.
  - Check it: screenshot the page loaded and held in its loading state (wide and phone) and compare side by side - the
    titles, labels and blocks must sit in the same places.
  - How to build one: copy the real component's JSX into `components/skeletons/<feature>/<Name>Skeleton.tsx` and swap
    each data expression for a `Skeleton` bar (`@/components/ui/skeleton`); for lists, a typical number of rows of the
    real row markup. Share the real texts instead of copying them where you can (export the page's tab list, headings,
    labels - e.g. `TOTAL_LABELS` in attendance's labels.ts, `PROFILE_TABS`, `OFFER_GROUPS`); a copied list gets a
    "change both together" comment. Root element: `role="status"` and `aria-label` from a `label` prop. Match the real
    rows' count and height so nothing jumps when the data arrives. On a dark (`bg-hero`) block, draw the block dark and
    the bars with `bg-hero-foreground/10`, so it does not flash light first.
  - `common/` holds only skeletons of UI that several modules share: `HeaderSkeleton` (the header's menu and account chip
    while accounts.me loads), `TodayCardSkeleton` (home + attendance), `ChangeHistorySkeleton` (ChangeHistoryList), `TimelineSkeleton`
    (JobTimeline), `PairsSkeleton` (real labels with value bars), `ListSkeleton` / `RowsSkeleton` (simple rows). A module
    skeleton that a second module needs moves to `common/`. No generic "shape" skeletons that ignore the real layout.
  - Only what loads becomes a skeleton: the page title, tabs, search and filters stay usable.
  - **One skeleton per page load, never two in a row** (the user, 2026-11-22). The layout and the page do not wait for
    accounts.me (RequireLogin shows them at once, so the page's data loads at the same time); anything that depends on
    the access - a redirect, which tabs exist, which tab an address asks for - waits for `useAccess().ready` instead of
    treating "not loaded yet" as "no access". A part that needs the user (one's own code) shows the page's skeleton
    until `me` is there, never `null`.
  - Text stays only where a skeleton cannot go: the placeholder option of a dropdown ("Loading…") and a button's own
    busy label ("Saving…").

## 7. API tracker - MANDATORY

`API_TRACKER.md` lists every API so the system is understandable and nothing is built twice.

- **Before creating an API, search the tracker.** If an existing API does the same thing - or can with a small
  optional input - extend it instead. Never add a second API for the same job.
- **Every API change updates the tracker in the same change:** new, removed, renamed, input or output changed,
  access changed, or behaviour changed.
- Each API has a ``### `path` `` entry with: HTTP path and code folder, **access** (area + level, e.g. "Onboarding: Edit"),
  **scope** (a `- **Scope:**` line: how data access limits it - whose records it covers, or "not limited by data access"
  and why), **input** (every field: type, required, rules), **returns**, **what it does**, and **errors**. It also appears
  in the Summary table, and "Total APIs" is kept correct.
- `npm run check:api-tracker` compares the tracker with the real router and fails on any missing, stale or
  duplicated entry, an entry without a Scope line, or a wrong total. It checks presence only - keeping the details
  accurate is your job.

## 8. Data access - MANDATORY for every new or changed API

Roles say WHAT someone may do (an area at View / Edit); data access says WHOSE records (company -> plant -> department
rows on each role given to them - decided 2026-11-18, BACKLOG 3a). It is **not automatic**: Prisma does not filter on
its own (decided 2026-11-18 - an automatic filter would silently give wrong answers to the queries that must see every
company). So for **every API you create or change**, work through this checklist **before writing code**, and say in
your answer which rule the API follows.

1. **Decide its rule** and write it as the API's `- **Scope:**` line in `API_TRACKER.md` (section 7): which area and
   level, whose records - or "not limited by data access" and why (own record, public link, a list shared by every
   company). Never leave an API that returns or changes people's records without a rule.
2. **The service gets the logged-in user** (`context.user` -> `viewer: CurrentUser`), not only their id.
3. **A list** of people's records (employees, candidates, or a table with an `employeeId` / `candidateId`): the service
   passes `scopeOf(viewer, area, level)` and the repository function takes a **required** `scope: DataScope` (directly
   or in its filter type) and applies `scopeWhere(scope)` **inside an `AND` list** (or nested on its own, e.g.
   `employee: scopeWhere(scope)`) - never spread next to another `OR`, which would overwrite it. Counts, group-bys,
   tiles and exports of that list use the same scope.
4. **One record** by id / code: `getEmployeeFor` / `getCandidateFor`, or `hasLevelAt(viewer, area, placement, level)` -
   outside the View range `NOT_FOUND` (never reveal it exists), View only for a change `FORBIDDEN`. Parts of an employee's
   record: `seesPart` / `assertPart`. A record that hangs on a person (a document, a letter, a task, a day): check that
   person first.
5. **A change**: Edit covering the record (`assertCanChange`, `getCandidateFor(..., 'WRITE')`); a **move** (company / plant
   / department) needs Edit on the old **and** the new placement; a **new** record needs Edit where it is placed
   (`assertCanPlace`). Bulk changes (imports, uploads, rosters) check **every row's** person.
6. **Settings**: something one company or plant owns (its details, plants, a plant's departments, its holiday lists) ->
   `assertWholeSlice`; something every company shares (master lists, shifts, patterns, roles, security rules, letter
   templates, joining task types) -> `assertGroupWide`.
7. **Relationships, not rows**: one's own record, the reporting tree and the HOD department (`employees.hods`) are worked out in
   the service - pass `SYSTEM_SCOPE` with the explicit ids. `SYSTEM_SCOPE` otherwise only for scripts, background jobs and
   steps with no logged-in person - never for what an API returns to a user.
8. **A read that must see every company** (a uniqueness check, the code series, names of who did something, a picker,
   a job): allowed, but write why right above the repository function: `// data access: <reason>`.
9. **E-mails about people** (reminders, notifications to HR): only to those whose data access covers the person
   (`accountsService.mailRecipients(area, level, placement)` / `mailRecipientsFor`).
10. **Frontend**: forms offer only what the user may choose - `useAccess().covers(area, level, where)`.
11. **Test it**: add the outside-range case to `backend/tests/data-access-*.test.ts` (someone limited to company A gets
    "not found" / an empty list for company B).
12. **Run** `npm run check:data-access` - it fails on any repository function that reads people's records in bulk
    without a `DataScope` or a `// data access:` reason - and `npm run check:api-tracker` (the Scope line).

When you change an existing API, re-read its Scope line and keep it true.
